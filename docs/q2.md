## Shared CPU primitives

include/bh/parallel.hpp exposes:

~~~cpp
std::vector<std::uint64_t> prefix;
bh::exclusive_scan_omp(costs, prefix); // n+1 entries: 0, cumulative costs, total
std::vector<std::int32_t> order;
bh::radix_order_omp(tree.key, order);  // ascending (Morton key, original index)
~~~

The scan uses balanced contiguous blocks, local scans, a serial scan of the small team-offset array, and parallel offset addition. Input/output must be distinct and the total must fit uint64_t. Particle counts and 32-bit costs fit within that limit under the existing CLI index bound.

The stable radix sort makes eight 8-bit LSD passes over all 64 bits. Each thread builds a histogram for a contiguous input block. Bucket/thread offsets are computed in deterministic order, and workers scatter to disjoint ranges. Original indices are initialized in ascending order, so equal Morton keys retain ascending particle index. No third-party parallel algorithms are used. Keys and particle arrays remain unchanged; the tree owner can reuse the resulting order without changing any tree representation.

Both algorithms use the actual team size inside each parallel region; an OpenMP runtime may shrink a team. The partition_begin() helper handles more workers than elements.

## Force scheduling and particle identity

~~~bash
./bh --backend omp --force static --threads 8 --force-order morton
./bh --backend omp --force dynamic --threads 8 --chunk 16
./bh --backend omp --force guided --threads 8 --chunk 16
./bh --backend omp --force costzones --threads 8
./bh --backend omp --force dynamic --threads 8 --force-order original
~~~

All strategies use the same tree-walk implementation as the sequential reference. Each step sorts Morton keys into an index permutation and physically packs the force SoA fields (positions, mass, outputs, and cost) into that order. An inverse map translates original leaf IDs to packed source indices; each target still uses its original ID to exclude self-interactions and read its Morton key. Outputs scatter back to the persistent original-order particles before integration or validation.

This implements the proposal's physical force-data reordering without changing the shared tree representation or persistent particle identity. Original leaf links and the validation sample remain stable. Historical costs follow particle identity even as Morton order changes. The locality control measures the combined effect of spatial work order, contiguous packed force fields, inverse-map lookups, and all required sorting/gather/scatter overhead. Velocities are not used by the force walk and need no temporary copy.

The original force order bypasses sorting. Chunk 0 means contiguous static allocation and chunk 1 for dynamic/guided; a positive value requests that exact OpenMP chunk. Costzones requires Morton order and does not use chunk. Sequential force ignores order/chunk and reports original order in CSV.

Costzones assigns unit costs on the first step. Later it snapshots every particle's previous cost in the current Morton order before workers overwrite costs. A parallel exclusive scan produces cumulative costs; binary searches at approximately equal fractions of the total produce continuous Morton ranges. All-zero history falls back to equal particle counts. Cuts use the **actual** force team size. Empty ranges are allowed; targets are never dropped or duplicated. Reloading a backend resets the history flag.

## Measurement definitions

- force_s includes allocation, sorting/gather/scatter, history snapshot, scan/cuts, traversal, synchronization, and work instrumentation. Reordering is charged every step, even if a future builder could share its permutation.
- force_order_s includes sorting, gathering and output scattering. force_partition_s and force_walk_s cover partitioning and traversal. These are nonoverlapping diagnostic intervals measured with the driver's monotonic clock. Total force time also contains setup/cleanup gaps. Partition time is zero for static/dynamic/guided.
- threads is the requested OpenMP limit; actual_threads is the actual **force** team size. Sequential force reports one worker even on an OpenMP backend.
- thread_interactions is the semicolon-separated uint64_t work array, including idle workers. Its sum equals interactions.
- load_imbalance = max(Wp) * actual_threads / sum(Wp). When all work is zero it is defined as 1 (perfect balance).
- warmup and is_warmup retain raw rows while identifying excluded steps. CSV uses 17-digit precision. Appending to an incompatible existing header fails.

Interaction counts measure work, not cache stalls or equal wall time per interaction. Small serial offset computations scale with worker count, not particle count.

## Correctness checks

~~~bash
make test
make test-cli
make PRECISION=double test-parallel
make PRECISION=double test-cli
CONFIGS="--backend omp --force costzones --threads 3" \
  BH=./bh_double bash tests/run_tests.sh
~~~

test_parallel.cpp checks scans against serial sums and permutations against an independent stable-sort reference. It tests weighted/zero/large-total cuts and complete coverage. Multi-step force checks cover seq/lock trees, all four workloads, tiny/uneven inputs, different worker counts/chunks, and bit-identical particle outputs against a sequential walk on the **same tree**.

Independent lock builds can order duplicate-key leaf chains differently, causing tiny floating-point differences on degenerate inputs; this predates Q2. Physics tests check error/energy/tree validity, while scheduling tests share a tree. Parallel validation reductions may differ in the final double bits, so CSV tests use tight tolerances for reduced diagnostics and exact comparisons for integer counts.

## Reproducible Q2 experiments

In this Windows checkout, GCC 15.2.0/OpenMP and Python/matplotlib were installed under the workspace's sibling .tools directory, without changing the system PATH. To use them in a new PowerShell session, dot-source the environment helper:

~~~powershell
. .\scripts\windows-env.ps1
mingw32-make -j4
python tests\test_cli.py
~~~

~~~bash
python3 -m pip install -r requirements-analysis.txt
make -j
python3 scripts/run_q2.py --config experiments/q2-local.json --output results/q2-local
python3 scripts/analyze_q2.py --input results/q2-local --output docs/results/q2-local
~~~

Add --dry-run to print the case list. Output directories must be new to prevent duplicate appends. Each run retains raw CSV and a log. The combined steps.csv, configuration, randomized execution order, actual commands, OpenMP environment, hardware/OS, compiler, binary SHA-256, git status, and a source ZIP are saved. A failure or unexpected actual team size stops the study. Run one study at a time with other CPU-heavy work idle.

q2-local.json: N=20,000 strong scaling; fixed N/p=2,000 weak scaling; 1/2/4/8/16 workers; three repeats; two warmup steps; theta=0.5; seed 42. It includes three distributions, Morton/original controls, default chunk 1 versus 16 for dynamic/guided, and a 1,400-step N=3,000 collision history. Sequential tree construction holds non-force stages constant. Passive OpenMP waiting and no binding are used on Windows; record these settings when comparing machines.

q2-full.json is the formal-hardware profile: N up to 10^6, lock tree construction, more chunks/repeats, core binding, and longer collision histories. Adjust workers to the machine and use a fresh output directory. Final hardware experiments, GPU validation support, integration with a future Morton builder, and the group report/slides remain team integration tasks.

### Aggregation and formulas

Discard warmup steps, take each metric's median within a run, then take the median across repeats. Error bars are min/max per-repeat medians, not confidence intervals.

~~~text
force speedup = Tseq_force(N) / Tp_force(N)
force efficiency = force speedup / p
total speedup = Tseq_total(N) / Tp_total(N)
total efficiency = total speedup / p
strategy speedup = T1_force(N, same strategy/order/chunk) / Tp_force(N, same strategy/order/chunk)
weak time efficiency = T1_force(Nbase, same strategy) / Tp_force(p*Nbase, same strategy)
~~~

Use matching-N sequential baselines for speedup. Fixed N/p is not strictly fixed work per worker because Barnes-Hut work also depends on depth, distribution and interactions. Matching-N speedup and weak time efficiency are different columns. Low lambda alone does not establish a faster strategy: compare full force time and ordering/partition cost.

Collision figures use 25-step bins across repeats, including the initial fallback. The x coordinate is post-drift time; force/cost were evaluated just before that drift. Raw per-step CSV preserves unsmoothed diagnostics.
